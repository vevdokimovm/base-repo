# CHANGELOG — `deploy.sh`

> Собственная история деплойера. Скрипт живёт своей жизнью внутри репы: он меняется
> чаще, чем сама база, и его поведение нужно уметь откатывать и объяснять отдельно.
> Правило — `00-infrastructure/44-what-to-version.md` (у меняющихся инструментов
> обязательны версия и журнал).
>
> Версия скрипта — в переменной `SCRIPT_VERSION` в шапке файла.
> Формат записей — `00-infrastructure/42-release-description-standard.md`.

## [3.0.1] — 2026-07-29 — Только яркие цвета (PATCH)

Тёмный текст на чёрном фоне не виден. Прошлые правки убирали конкретные проявления —
сначала переменную, потом функцию, — но не запрещали сам класс. Теперь запрет описан
как белый список и проверяется тестом.

### Fixed
- **Все цвета переведены на яркие (91–97).** Было: `31–36` — тусклые варианты палитры,
  `1m` без цвета у `bld()` и печать вообще без кода у `plain()` — оба брали цвет терминала
  по умолчанию, а он на тёмной теме тёмный. Стало: каждая функция печати несёт свой
  яркий код, `bld()` — `1;97`, `plain()` — `97`.

### Added
- **Тест I4 переписан на белый список.** Допустимы только `0m`, `1;97m`, `91–97m`;
  любой другой код валит тест. Плюс проверка, что каждая из семи функций печати
  действительно печатает со своим цветом, а не полагается на терминал.

### Verified
- 208 проверок зелёные, 58 кейсов.

## [3.0.1] — 2026-07-29 — Только яркие цвета (PATCH)

Прошлые две правки цвета били мимо. Убрал `dim`, но не заметил главного: две функции
печатали **без кода цвета вообще** — `bld()` только жирностью, `plain()` вообще ничем.
Обе брали цвет терминала по умолчанию, а он на тёмной теме тёмный. Плюс остальные
использовали тусклые варианты палитры (31–36), которые на чёрном фоне тоже плохо читаются.

### Fixed
- **Вся палитра переведена на яркие коды**: `91` красный, `92` зелёный, `93` жёлтый,
  `95` пурпурный, `96` голубой, `97` белый, `1;97` жирный белый.
- **`bld()` и `plain()` больше не полагаются на цвет терминала** — каждая строка несёт
  собственный яркий код.
- Запрещены и проверяются тестом: `30m` (чёрный), `90m` (серый), `2m` (тусклый),
  голая жирность `1m`, печать без кода.

### Added
- **Тест I4 ужесточён до белого списка**: в скрипте допустимы только `0`, `97`, `1;97`,
  `91`, `92`, `93`, `95`, `96`. Любой другой код — падение. Плюс проверка, что каждая
  из семи функций печати выводит со своим цветом.

### Verified
- 208 проверок зелёные, 58 кейсов.

### Notes
- Три захода на один баг, потому что дважды чинил симптом: сначала обнулил переменную,
  потом удалил функцию, и только на третий раз проверил **каждую** точку вывода. Правильный
  порядок был обратный — сразу перебрать все места, где что-то печатается.

## [3.0.0] — 2026-07-29 — Цвет, чистка ассетов и подсказка об удалении (MAJOR)

Три претензии владельца, все обоснованные: тусклый текст не виден на тёмном фоне; чистка
дублей-ассетов требовала спецфлага, о котором надо помнить; про освобождение диска скрипт
не говорил вообще ничего, хотя режим для этого есть.

### Changed
- **MAJOR: чистка дублей — часть приведения к стандарту, а не отдельный флаг.** Ассет той
  же версии под старым именем нарушает §42 («ровно три ассета»), поэтому снимается при
  обычной ревизии (`AUDIT`/`FORCE`/`ALL_REPOS`). Владелец не обязан помнить спецкоманду,
  чтобы получить релиз по стандарту. Страховка — `KEEP_LEGACY_ASSETS=1`.
- **Подсказка об освобождении места печатается в конце каждого прогона**, а не ждёт,
  пока про режим `VERIFY` вспомнят.

### Fixed
- **Тусклый цвет вырезан из скрипта полностью.** Прошлая правка обнулила переменную,
  но оставила функцию `dim()` и само понятие. Теперь нет ни функции, ни переменной,
  ни атрибута `2m` нигде в файле — второстепенное печатается обычным цветом терминала.
  Проверяется тестом по исходнику **и** по выводу.

### Added
- **Тест I4** — в скрипте нет `2m`, нет `30m`, нет `C_DIM`, и в реальном выводе нет dim.
- **Тест A7** — подсказка про `VERIFY=1` есть в каждом прогоне.

### Verified
- 202 проверки зелёные, 58 кейсов.

### Notes
- Урок: «обнулил переменную» ≠ «убрал возможность». Пока функция существует, ею
  воспользуются — надо удалять сущность, а не значение.

## [2.2.0] — 2026-07-29 — Полная ревизия: покрытие считается, а не оценивается (MINOR)

Баги находились только тогда, когда на них показывал владелец. Значит дело не в отдельных
багах, а в способе тестирования: тесты писались под каждый найденный дефект, то есть
покрывали лишь те пути, по которым уже прошёл человек. Проведена системная ревизия —
инвентаризация всех режимов, статический анализ, перечень деструктивных операций.
Отчёт: `reports/testing/deploy_audit.md`.

### Fixed
- **`VERIFY` не работал вообще.** Блок стоял в файле раньше объявления `gh_try` и
  `release_state` — каждый вызов падал с `command not found`, ошибка глушилась, и режим
  всегда отвечал «ДЕРЖАТЬ». То есть инструмент, отданный для решения об удалении архивов,
  не мог сказать «безопасно» ни при каких условиях. Все функции подняты выше первого
  исполняемого шага.
- **Список к удалению ломал `xargs`.** Пути писались с отступом, как в выводе на экран.
  Отступ срезается; тест проверяет не формат, а что `xargs` реально находит файлы.
- **Мёртвый код.** `CL_USED` и `IS_NEW` удалены. `SCRIPT_VERSION` не использовалась —
  теперь печатается первой строкой вывода, чтобы по логу было видно, какая ревизия отработала.

### Added
- **Тесты 52–56**: `VERIFY` (полный комплект / нет ассета / нет релиза / никогда не
  публиковался), `PRIVATE` (приватность по умолчанию и `PRIVATE=0`), переопределение
  `SERVICE_RE` / `REPO_MAP` / `VARIANT_REPOS` / `MIN_FILES`, режим `ASSET=0`.
- **`reports/testing/deploy_audit.md`** — методика ревизии, найденное, проверенное-и-исправное,
  команда инвентаризации покрытия для будущих версий.

### Verified
- 197 проверок зелёные, 56 кейсов.
- `shellcheck -S warning`: чисто. Предупреждения SC2221/SC2222 проверены **запуском**
  на пяти входах и признаны ложными — shellcheck не разбирает перенос строки в списке
  паттернов `case`.
- Режимов без тестов: 3 из 20 (`BRANCH`, `RETRIES`, `GH_TIMEOUT`) — низкий риск, осознанно.

### Notes
- Правило: новый флаг не считается готовым, пока по нему нет теста. Код, который не
  выполнялся ни разу ни в одном тесте, — не рабочий код, а предположение о том, что он рабочий.

## [2.1.2] — 2026-07-29 — Чистка ассетов приведена в безопасный вид и покрыта тестами (PATCH)

Разрушительная операция (удаление ассетов) была написана, но **ни разу не выполнялась**:
в стабе `gh` не было `delete-asset`, а тестов на неё не существовало. Проверка по прямому
вопросу владельца вскрыла в этом коде два содержательных дефекта — оба закрыты, путь
покрыт тестами, включая проверки того, что удалять **нельзя**.

### Fixed
- **Удаление шло ДО загрузки канонического ассета.** При обрыве сети между удалением и
  загрузкой релиз оставался вообще без ассета — необратимая потеря. Теперь чистка идёт
  отдельным блоком **после** загрузки и только если канонический ассет подтверждён
  на релизе; иначе пропускается с пояснением.
- **Чистка была недостижима в реальном сценарии.** Код сидел внутри ветки «канонического
  ассета нет». У уже обработанных релизов ассет есть, значит ветка не выполнялась и флаг
  не делал ничего. Вынесен в самостоятельный блок.

### Added
- **Предупреждение о бесполезном флаге.** `DROP_LEGACY_ASSETS=1` без `AUDIT`/`ALL_REPOS`
  не обходит опубликованные релизы — скрипт говорит об этом прямо, а не молчит.
- **`DRY=1` покрывает и чистку**: показывает, что снял бы, ничего не удаляя.
- **Тесты 49–51.** Что снимается: дубль той же версии в обоих написаниях
  (`v6.6.0` и `v6_6_0`). Что **не** снимается: канонический ассет, zip другой версии,
  не-zip вложения. Что не происходит: без флага — ничего, при `AUDIT+FORCE` без флага —
  ничего, в `DRY` — ничего, без канонического ассета — ничего.
- **Стаб `gh` научился `delete-asset`** — до этого путь физически не мог выполниться в тестах.

### Verified
- 174 проверки зелёные, 51 кейс.

## [2.1.1] — 2026-07-29 — Читаемый вывод и точечная чистка ассетов (PATCH)

Второстепенные строки печатались атрибутом «тусклый» — на тёмной теме терминала это
чёрное на чёрном, текст не виден вообще. Плюс уточнено, что именно снимает чистка
легаси-ассетов, чтобы флаг не мог задеть лишнее.

### Fixed
- **Невидимый текст.** Атрибут `\033[2m` (dim) убран совсем: второстепенное печатается
  обычным цветом терминала и читается на любой теме — светлой и тёмной.
- **`DROP_LEGACY_ASSETS` бил слишком широко.** Раньше снимал любой `.zip`, кроме
  канонического. Теперь — только архив **той же версии** под старым именем
  (`finpilot_v6_6_0_intl.zip` при канoне `personal-finance-dss-v6.6.0.zip`), в обоих
  написаниях версии. Прочие вложения не трогаются: удаление ассета необратимо.

### Added
- **`templates/deploy-MODES.md`** — справочник по всем режимам и ключам: пять команд на
  все случаи, таблицы по области и глубине работы, рецепты, «чего скрипт не делает
  никогда». Ссылка на него — в шапке самого скрипта.

## [2.1.0] — 2026-07-29 — Ревизия всех реп системы, чистка легаси-ассетов (MINOR)

`AUDIT=1` брал только те репы, для которых в папке нашлись архивы, — репу без свежей
зипки было не проверить вообще. Теперь список можно взять из `repos-map.md`: ревизия
охватывает всю систему, а не только то, что лежит в Downloads.

### Added
- **`ALL_REPOS=1`** — список реп из `repos-map.md` (фолбэк — `gh repo list`), включает
  `AUDIT` автоматически. Репозиторий проверяется, даже если архива в папке нет.
- **`DROP_LEGACY_ASSETS=1`** — снимает с релиза ассеты со старым неканоничным именем.
  По §42 ассетов ровно три, а после бэкфилла у части релизов их четыре: канонический
  и легаси рядом. Удаление необратимо, поэтому только по явному флагу.
- **Тест 48** — репа из карты без архива в папке: без флага не трогается, с `ALL_REPOS=1`
  подхватывается и приводится к стандарту.

### Fixed
- **Имена реп из карты извлекались не полностью.** Шаблон требовал бэктик сразу после
  решётки, а авто-регистрация пишет `## 🆕 \`repo\`` — то есть ровно те репы, которые
  завёл сам деплойер, в список не попадали. Теперь берётся первое имя в бэктиках из
  любой строки-заголовка.

### Verified
- 162 проверки зелёные, 48 кейсов.

## [2.0.0] — 2026-07-28 — Режимы, ретраи, проверка перед удалением архивов (MAJOR)

Первый полный боевой прогон по всем репам занял около двух часов, потому что скрипт
на каждом запуске проходил ревизию всех релизов подряд. Теперь по умолчанию он делает
только то, ради чего запускается: публикует новые версии из папки. Ревизия истории
вынесена в отдельный режим. Заодно закрыты три дефекта, которые вскрыл прогон на
нестабильной сети, и добавлена проверка «что уже безопасно удалить локально».

### Changed
- **MAJOR: дефолт изменён.** `zsh deploy.sh` = коммит + тег + релиз только для новых
  версий из папки. Проверка старых релизов больше не запускается автоматически.
- **`AUDIT=1`** — полная ревизия всех релизов всех реп (прежнее поведение по умолчанию).
  `REPAIR=1` и `FORCE=1` включают её автоматически.

### Added
- **`SCRIPT_VERSION`** в шапке + этот журнал.
- **`VERIFY=1`** — проверка перед удалением локальных архивов: для каждого архива
  сверяет наличие тега, релиза и канонического ассета на GitHub. Безопасные пишет
  в `~/Downloads/safe_to_delete.txt`, остальные показывает с причиной.
- **`GH_TIMEOUT`** (по умолчанию 120 с) — предел на один вызов `gh`.
- **`gh_try`** — ретраи с нарастающей паузой, но **только** на признаки сбоя связи
  (таймаут, обрыв, 502/503/504, rate limit). «Не найдено» и отказы прав не ретраятся.
- **`release_state`** — отличает «релиза нет» от «запрос не прошёл». При сбое связи
  версия помечается и пропускается, а не считается отсутствующей.

### Fixed
- **`FORCE=1` валил версии без секции в CHANGELOG.** Пустой notes-файл уходил в
  `gh release edit --notes-file`, и версия падала с «не удалось обновить». Теперь тело
  правится только когда есть чем; при отсутствии секции описание и заголовок остаются
  как были, а версия называется в выводе.
- **Утечка `TITLE` между итерациями.** Если notes-файл уже был создан на этапе публикации,
  `build_notes` не вызывался — и версия получала заголовок предыдущей. Так тег `v1.17.0`
  base-repo получил заголовок v1.18.0. Теперь заголовок считается заново для каждой версии.
- **Разнобой шапок в теле релиза.** Секции вида `## vX.Y.Z — …` (без скобок) уезжали
  в релиз как есть, и такие релизы выглядели иначе. Шапка нормализуется к канону
  `## [X.Y.Z] — дата — тезис (BUMP)`; содержимое секции не трогается.
- **Зависание на нестабильной сети.** Вызовы `gh` шли без таймаута — прогон мог стоять
  десятками минут на одной версии.

### Verified
- 158 проверок зелёные, 47 кейсов. Новые: 45 (FORCE без секции), 46 (нормализация шапки),
  47 (дефолт не запускает ревизию, `AUDIT=1` запускает).
